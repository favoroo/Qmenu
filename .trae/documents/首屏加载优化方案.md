# Q 菜单 首屏加载优化方案

## 摘要

用户反馈每次首次进入小程序时，菜谱和头像/昵称都要过一会儿才能加载出来。经代码分析，这**不是测试版的原因**，正式版也会同样表现。根本原因是架构层面的问题：6-7 个串行网络请求 + 零本地数据持久化 + 无加载状态。本方案通过增加本地缓存层、并行化云端查询、预加载缓存数据等手段，将冷启动首屏从秒级降至百毫秒级。

## 是否测试版原因

**不是。** 这是代码架构问题，正式版会同样表现。测试版唯一可能加重的是云函数冷启动频率（流量低导致实例更易被回收），但根本症结在代码：

- 6-7 个串行网络请求，每个 200-500ms，冷启动总计 3-10s+
- `cloudCache` 仅存内存，App 重启后全部丢失
- 无骨架屏/加载状态，白屏期间用户感知差

## 当前状态分析

### 加载流程（冷启动）

```
app.onLaunch
  └─ login 云函数 (#1, 200-500ms)
      └─ db.initCloudData() 无 groupId → 空操作（无效调用）
kitchen.onShow
  └─ await loginPromise（等待 #1 完成）
      └─ getGroup 云函数 (#2, 200-500ms)
          └─ db.initCloudData(groupId) 串行 4 个 DB 查询:
              ├─ categories.get() (#3)
              ├─ recipes.get()     (#4)
              ├─ orders.get()      (#5)
              └─ cart.get()        (#6)
                  └─ loadData() 从内存读 → setData 渲染
order.onShow
  └─ getGroup({groupId}) (#7, 重复调用!)
```

### 7 个确认的问题点

| # | 位置 | 问题 |
|---|---|---|
| 1 | `utils/db.js` cloudCache | 仅内存，App 重启全丢 |
| 2 | `utils/db.js` initCloudData | 4 个 DB 查询串行 await |
| 3 | `app.js:30` | `db.initCloudData()` 不传 groupId，立即 return（无效） |
| 4 | `pages/order/index.js:64-67` | 重复调用 getGroup |
| 5 | `pages/kitchen/index.wxml` | 加载期间无骨架屏/占位 |
| 6 | `utils/db.js` currentGroupId | 未本地缓存，必须等 getGroup 返回 |
| 7 | `pages/kitchen/index.js:88` | onShow 串行 await login 后才发 getGroup |

## 架构决策

### 决策 1：本地缓存层 + 后台刷新（核心）
在内存 `cloudCache` 之上增加 `wx.setStorageSync` 持久化，按 `groupId` 隔离。启动时**同步**从本地装填 `cloudCache`（微秒级），立即渲染；随后**异步**从云端刷新，完成后二次 `setData`。不破坏现有同步 db API 风格。

### 决策 2：缓存键设计
| 存储键 | 内容 | 用途 |
|---|---|---|
| `cloudData_{groupId}` | `{categories, recipes, orders, cart, updatedAt}` | 按 groupId 隔离的业务数据 |
| `lastGroupId` | groupId 字符串 | 启动时预加载，免去等待 getGroup |
| `cachedGroupsList` | groups 数组 | order 页复用，避免重复 getGroup |

### 决策 3：initCloudData 改 Promise.all
4 个查询相互独立，可安全并行。默认数据播种逻辑仅在「首次进入空群组」时触发，仍在各自分支内处理。

### 决策 4：login + getGroup 暂不合并
缓存层已让 getGroup 在热启动近乎零成本。合并需改云函数 + 多处调用点，边际收益不足以承担耦合风险。列为后备方案。

## 实施方案

### Phase 1：db.js 增加本地缓存层与并行化

**文件**：`utils/db.js`

**改动 A — 新增缓存常量与方法**

在文件顶部新增缓存键常量：
```js
const CACHE_PREFIX = 'cloudData_';
const LAST_GROUP_KEY = 'lastGroupId';
const GROUPS_LIST_KEY = 'cachedGroupsList';
```

在 `db` 对象内新增方法：
- `loadFromLocalCache(groupId)` — 同步从 storage 装填 cloudCache，返回 boolean
- `saveToLocalCache(groupId)` — 将 cloudCache 落盘到 storage
- `setLastGroupId(groupId)` / `getLastGroupId()` — 持久化最后使用的 groupId
- `cacheGroupsList(groups)` / `getCachedGroupsList()` — 群组列表缓存，供 order 页复用

**改动 B — 重构 initCloudData 为并行 + 落盘**

将原有串行的 4 个 DB 查询改为 `Promise.all` 并行执行：
```js
const [categories, recipes, orders, cart] = await Promise.all([
  this._fetchCategories(dbInstance, gid),
  this._fetchRecipes(dbInstance, gid),
  this._fetchOrders(dbInstance, gid),
  this._fetchCart(dbInstance, gid)
]);
```

拆分出 4 个独立的 `_fetchXxx` 方法（各自自洽，含默认数据播种逻辑）。获取完成后调用 `this.saveToLocalCache(gid)` 落盘。catch 分支降级读本地缓存。

**改动 C — 写操作同步落盘**

在 `saveCategories`、`saveRecipes`、`saveCart`、`saveOrders`、`addRecipe`、`updateRecipe`、`deleteRecipe`、`deleteOrder`、`createOrder` 等修改 `cloudCache` 的方法末尾追加 `this.saveToLocalCache(currentGroupId)`。

### Phase 2：app.js 预加载缓存 + 移除无效调用

**文件**：`app.js`

**改动 A — onLaunch 增加本地缓存预加载**

在 `this.globalData.loginPromise = this.login()` 之前，同步执行：
```js
const lastGroupId = db.getLastGroupId();
if (lastGroupId) {
  db.setCurrentGroupId(lastGroupId);
  db.loadFromLocalCache(lastGroupId); // 同步装填 cloudCache，无网络开销
}
```

**改动 B — 移除 login() 中无效的 initCloudData 调用**

删除 `app.js` 中 `await db.initCloudData()` 这一行（不传 groupId 是空操作，且 login 不应承担数据加载职责）。

### Phase 3：kitchen 页两阶段渲染

**文件**：`pages/kitchen/index.js`

**改动 A — data 增加 loading 状态**
```js
loading: true,
isBackgroundRefresh: false,
```

**改动 B — onShow 分两阶段渲染**

- **阶段 1（瞬时）**：同步读本地缓存，立即 `loadData()` 渲染，设置 `loading: false`
- **阶段 2（后台）**：`await loginPromise` → `loadGroupsList()` → 云端刷新完成后二次 `setData`

**改动 C — loadGroupsList 缓存 groups + 持久化 lastGroupId**

获取群组后调用 `db.cacheGroupsList(groups)` 和 `db.setLastGroupId(currentGroupId)`。

**改动 D — onGroupChange 切换群组时也走缓存优先**

先 `loadFromLocalCache(newGroupId)` + `loadData()` 瞬时渲染，再后台 `initCloudData` 刷新。

### Phase 4：kitchen 页骨架屏

**文件**：`pages/kitchen/index.wxml` + `pages/kitchen/index.wxss`

在菜谱列表区域增加 shimmer 骨架屏，当 `loading && filteredRecipes.length === 0` 时显示：
- 左侧分类骨架（3 个占位条）
- 右侧菜谱骨架（4 个卡片占位）

WXSS 追加 shimmer 动画和骨架样式。

### Phase 5：my 页头像/昵称瞬时显示

**文件**：`pages/my/index.js`

将 `loadUserInfo` 改为两阶段：
- **阶段 1（同步）**：`wx.getStorageSync('userInfo')` 瞬时渲染
- **阶段 2（异步）**：`await loginPromise` 后用 `app.globalData.userInfo` 刷新

### Phase 6：order 页消除重复 getGroup

**文件**：`pages/order/index.js`

`loadOrders` 中优先从 `db.getCachedGroupsList()` 读取群组信息判断 admin，仅在缓存未命中时回退到云函数调用。

## 实施顺序

```
Phase 1 (db.js 缓存层 + 并行化)   ← 基础层，必须最先
   ↓
Phase 2 (app.js 预加载 + 移除无效调用)
   ↓
Phase 3 (kitchen 两阶段渲染)
   ↓ (并行)
Phase 4 (骨架屏)    Phase 5 (my 页)    Phase 6 (order 页)
```

Phase 1-3 为核心收益，Phase 4-6 为体验收尾。

## 预期效果

| 指标 | 优化前 | 优化后（缓存命中） | 优化后（首次无缓存） |
|---|---|---|---|
| 首屏可见菜谱 | 1.5-10s | **<100ms** | 骨架屏即时 + 云端刷新后填充 |
| 头像/昵称可见 | 200-500ms | **<50ms** | 同左 |
| 网络请求数 | 6-7 串行 | 5 并行（后台，不阻塞首屏） | 5 并行 |
| getGroup 重复调用 | 是 | 否 | 否 |

核心转变：**首屏渲染从「等待全部网络串行完成」变为「同步读本地缓存瞬时渲染 + 后台静默刷新」**。

## 风险与注意事项

1. **缓存陈旧性**：多用户协作场景最终一致，后台刷新后自动更新，对菜单类应用可接受。
2. **存储配额**：微信小程序本地存储上限 10MB，单群组缓存通常 <100KB，远低于上限。
3. **首次用户（无群组）**：`lastGroupId` 为空，跳过预加载，无回归。
4. **断网降级**：`initCloudData` catch 分支降级读本地缓存，UI 仍可用。
5. **既有 DB 查询 20 条限制**：属既有问题，非本次引入，后续可单独优化。

## 验证步骤

1. **Phase 1**：冷启动后 storage 有缓存数据；切换群组各自独立；杀进程重启 cloudCache 有数据；断网启动 UI 仍可用
2. **Phase 2-3**：冷启动 kitchen 页瞬时显示上次菜谱（<100ms）；后台刷新自动更新；全文搜索无 `db.initCloudData()` 无参调用
3. **Phase 4**：清缓存启动看到骨架屏；缓存命中不闪烁
4. **Phase 5**：冷启动 my 页头像瞬时显示；登录后自动刷新
5. **Phase 6**：冷启动进 order 页不触发 getGroup；admin 状态正确；缓存未命中回退正常
6. **全链路**：新增菜谱 → 杀进程重启 → kitchen 瞬时显示 → 下单 → 切 order 页无额外请求 → 数据一致
