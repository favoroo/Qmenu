# Q 菜单 数据存储优化方案（同步适配层）

## 概述

为微信小程序「Q 菜单」优化数据存储，解决三个核心问题：上传图片存的是不可靠的 `tempFilePath`（重启后丢失）、无任何压缩、`db.js` 与 `wx` 本地存储强耦合难以迁移服务器。采用「同步适配层」方案——新增图片压缩+持久化模块、为 `db.js` 引入可替换的存储适配层（保持同步 API）、补齐图片生命周期清理，使后续接服务器时主要改适配层实现，页面调用基本不动。

## 现状分析

- **图片存储不可靠**：`pages/recipe-add/index.js` 的 `chooseImage`/`chooseStepImage` 把 `wx.chooseMedia` 返回的 `tempFilePath` 直接存入 `data` 并最终入库。临时路径在小程序重启后会被系统清理，导致上传的封面图、步骤图全部丢失。
- **无压缩**：原图直接入库，浪费本地存储配额。
- **存储强耦合**：`utils/db.js` 中 12 处直接调用 `wx.getStorageSync`/`wx.setStorageSync`；`pages/order/index.js` 还有 2 处绕过 db 直接写 `DB_ORDERS` 键。迁移服务器需逐处改。
- **无图片清理**：删除菜谱（`db.deleteRecipe`）、重置数据（`my.resetCache`）都不清理已保存的图片文件，长期会撑爆 100MB 本地文件存储上限。
- **数据流**：`db.js` 管理 CATEGORIES/RECIPES/CART/ORDERS 四组 CRUD + `createOrder`/`formatTime`；`kitchen`/`order`/`discover` 页消费 `recipe.image` 与 `steps[].image`；默认图 `/assets/images/default_food.png` 是代码包只读资源。

### 关键 API 结论（已核实官方文档）

- `wx.compressImage`：返回压缩后 `tempFilePath`。`quality`(0-100) **iOS 仅对 JPG 有效**；`compressedWidth/Height`(基础库 2.26.0+) 对所有格式生效（等比缩放），低版本自动忽略。失败需降级。
- `FileSystemManager.saveFile`：把临时文件**移动**到本地，原 `tempPath` 失效，返回 `savedFilePath`。传 `filePath` 指向 `wx.env.USER_DATA_PATH` 下则保存为「本地用户文件」（重启可用、路径可识别）；错误码 `1300202`=超存储上限。
- `FileSystemManager.unlink`/`unlinkSync`：删除任意本地文件，含用户文件，有同步版本可用。

### 架构决策：采用「本地用户文件」模式

`saveFile` 传 `filePath = ${wx.env.USER_DATA_PATH}/recipe_imgs/xxx.jpg`：
- 产物为本地用户文件，重启后可用（满足持久化）；
- 路径含 `USER_DATA_PATH` 前缀，**真机/开发者工具均可靠识别**（区别于不透明缓存路径），删除用 `unlinkSync`；
- `resetCache` 可 `readdirSync`+`unlinkSync` 清空整个目录；
- 天然排除 `/assets/`（代码包只读）与 `https://`（未来云 URL），不会被误删/误重传。

### 同步/异步边界

- `db.js` 保持**同步** API（适配层封装同步的 `wx.getStorageSync/setStorageSync`）。
- 图片处理（`compressImage`+`saveFile`）本质异步，`utils/image.js` 返回 Promise；`recipe-add` 的 `submitForm` 改 `async`，存库前 `await`。
- 预留点：适配层把所有 wx 存储调用集中到一处；`image.js` 的 `storeImage` 按 `storageMode` 分本地/云分支。迁移服务器时替换 `storage` 对象为 `wx.request` 异步实现（届时 db 方法改 async，属下一阶段）。

## 改动详情

### 文件 1（新增）：`utils/image.js`

**What**：新建图片处理模块，封装「选图 → 压缩 → 本地持久化 → 删除」全流程，为云上传预留接口。

**Why**：集中管理图片生命周期；后续替换为 `wx.uploadFile` 只改本文件。

**How**：
- 配置对象 `CONFIG`：`storageMode: 'local'`（当前）| `'cloud'`（预留）；`compress: { quality: 80, maxWidth: 1080, maxHeight: 1080 }`。
- `isTempPath(p)`：判断是否 chooseMedia 临时路径（排除 `/assets/`、`USER_DATA_PATH`、`http(s)://`）。
- `isManagedLocalFile(p)`：是否本模块管理的本地持久化文件（含 `USER_DATA_PATH` 且含 `/recipe_imgs/`）。
- `compress(tempFilePath)`：调 `wx.compressImage`（quality + compressedWidth/Height），失败降级返回原路径。
- `saveLocal(tempFilePath)`：`ensureDir` 后 `fs.saveFile({ tempFilePath, filePath: ${IMG_DIR}/${genFileName()} })`，捕获 `1300202` 转友好错误。
- `uploadCloud(tempFilePath)`：预留，`wx.uploadFile` 上传返回 URL（未配置 `uploadUrl` 时 reject）。
- `storeImage(tempFilePath)`：统一入口，按 `storageMode` 走本地或云。
- `removeImageSync(filePath)`/`removeImagesSync(paths)`：同步删除托管文件，非托管静默跳过。
- `collectRecipeImages(recipe)`：收集菜谱封面+步骤图中所有托管本地图片。
- `clearAll()`：`readdirSync`+`unlinkSync` 清空图片目录，返回删除数。

导出：`CONFIG, storeImage, isTempPath, isManagedLocalFile, removeImageSync, removeImagesSync, collectRecipeImages, clearAll`。

### 文件 2（重构）：`utils/db.js`

**What**：引入同步存储适配层 `storage`，收敛全部 wx 存储调用；`deleteRecipe` 增图片清理；补 `saveOrders`/`deleteOrder`。

**Why**：隔离存储机制，迁移时只换 `storage` 实现；清理图片防 100MB 溢出。

**How**：
1. 顶部 `require('./image.js')`，新增适配层对象：
   ```js
   const storage = {
     get(key) { return wx.getStorageSync(key); },
     set(key, value) { wx.setStorageSync(key, value); return value; },
     remove(key) { wx.removeStorageSync(key); },
     clear() { wx.clearStorageSync(); }
   };
   ```
   附迁移指引注释：替换为 `wx.request` 调 REST API（届时需把 db 方法改 async）。
2. 把全部 12 处 `wx.getStorageSync/setStorageSync` → `storage.get/set`（`init`、`getCategories/saveCategories`、`getRecipes/saveRecipes`、`getCart/saveCart/clearCart`、`getOrders`、`createOrder` 末尾 set）。
3. `deleteRecipe(id)`：先 `find` 出目标菜谱，`imageUtil.removeImagesSync(imageUtil.collectRecipeImages(target))` 清图片，再 `saveRecipes(filter)` + `removeFromCartCompletely`。
4. 新增 `saveOrders(orders)`、`deleteOrder(orderId)`（供 order 页收口）。
5. `formatTime`/`createOrder`/`addRecipe`/`updateRecipe` 主体逻辑不变，仅内部 set 换 `storage.set`。

### 文件 3（修改）：`pages/recipe-add/index.js`

**What**：图片上传改用 image util；`submitForm` 改 `async`，存库前 `await` 图片持久化；编辑换图后清理旧图。

**Why**：存库前把 tempPath 转持久路径，解决重启丢失。

**How**：
1. 顶部 `require('../../utils/image.js')`。
2. `chooseImage`/`chooseStepImage`：保留 chooseMedia，仅把 tempPath 存入 data 用于预览（不在选图时持久化）。
3. `submitForm` 改 `async`，校验逻辑不变，try/finally 包裹：
   - 封面图：`if (isTempPath(imagePath)) finalImage = await storeImage(imagePath)`，否则保持原路径。
   - 过滤空行后再处理步骤图：`for` 循环对每个 `isTempPath` 的步骤图 `await storeImage`。
   - 组装 `recipeData`（image/均为持久路径）。
   - 编辑模式：先取 `oldRecipe`，`updateRecipe` 后用 `collectRecipeImages` 对比新旧，`removeImageSync` 删除被替换的旧图（防孤儿）。
   - 新增模式：直接 `addRecipe`。
   - `catch` 提示「图片处理失败，请重试」；`finally` 复位 `isSubmitting`。
4. `handleDeleteRecipe` 无需改动（`db.deleteRecipe` 内部已清图）。
5. WXML 无需改动（`imagePath`/`item.image` 仍驱动 `<image src>`）。

### 文件 4（修改）：`pages/my/index.js`

**What**：`resetCache` 在 `clearStorageSync` 前先清空本地图片目录。

**Why**：`clearStorageSync` 只清键值不清文件；重置后旧图残留持续占用配额。

**How**：`if (res.confirm)` 分支开头加 `require('../../utils/image.js').clearAll()`，其后保持原 `wx.clearStorageSync()` + `db.init()` + userInfo 重置逻辑。

### 文件 5（修改）：`pages/order/index.js`

**What**：第 51、110 行 `wx.setStorageSync('DB_ORDERS', orders)` 改走 db 适配层。

**Why**：db.js 之外唯一直接写 DB 键的地方，破坏隔离目标。

**How**：`completeOrder` 处改 `db.saveOrders(orders)`；`deleteOrder` 处删除整段 filter+set，改调 `db.deleteOrder(orderId)`。

### 不改动：`app.js` / `app.json`

- `app.js` 仅 `db.init()` + userInfo 初始化，适配层对它透明。
- `app.json` 路由/TabBar 无变化。`compressImage` 的宽高参数需基础库 2.26.0+（低版本自动忽略，不影响配置）。
- `kitchen/index.js:483`、`my/index.js:15`、`app.js:9` 的 `wx.getStorageSync('userInfo')` 属应用级用户设置，非 db 业务数据，保持不动（如需统一可另建 `utils/user-store.js`，非必需）。

## 假设与决策

1. **保持同步 db API**：用户选定同步适配层方案；页面调用风格不变，迁移服务器时再把 `storage` 换 `wx.request` 异步实现并将 db 方法改 async。
2. **图片存本地用户文件而非 base64**：base64 会撑爆 localStorage；本地文件+路径引用是服务器 URL 的自然类比。
3. **压缩参数**：`quality=80`、`maxWidth/Height=1080`（美食图清晰且体积可控）。iOS PNG 的 quality 无效但宽高缩放仍生效，失败降级保原文件。
4. **存储上限以 100MB 为安全阈值**：`saveLocal` 捕获 `1300202` 给提示；删除/重置清理是主要防线。
5. **删除菜谱后历史订单缩略图会失效**：`order` 页 `dish.image` 是下单时路径快照，删菜谱会删其图文件，历史订单该菜缩略图空白。离线 Demo 可接受；可选增强：给 `<image>` 加 `binderror` 回退默认图（不在核心计划）。
6. **同步清理阻塞可忽略**：`unlinkSync` 处理的文件少且小。
7. **云迁移路径**：未来 `image.js` 设 `storageMode='cloud'`+`uploadUrl`，`db.js` 换异步 `storage`；`recipe-add` 的 `await storeImage` 结构已就绪。

## 验证步骤

**图片模块**：
1. 新增菜谱选封面图 → 持久路径含 `USER_DATA_PATH/recipe_imgs/`。
2. 完全重启小程序 → 编辑该菜谱，封面与步骤图仍显示（持久化生效）。
3. 选 >3MB 大图 → 保存后 `wx.getFileInfo` 看 size 明显变小（压缩生效）。
4. iOS 选 PNG 截图 → 不报错能保存（降级生效）。
5. 临时设 `storageMode='cloud'`+假 `uploadUrl` → `storeImage` 走 `wx.uploadFile` 分支（接口预留验证，验证后还原）。

**存储适配层**：
1. `db.js` 全文搜 `wx.getStorageSync`/`wx.setStorageSync` 应为 0 处。
2. 厨房页分类/菜品/购物车计数正常。
3. 删除带图菜谱 → `accessSync(savedPath)` 抛「文件不存在」（图片已删）。
4. 临时把 `storage.get` 改返回固定 JSON → 页面用上模拟数据（替换点可工作，验证后还原）。

**recipe-add 页**：
1. 新增选封面+2 步骤图 → 重启 → 编辑该菜谱图片仍在。
2. 编辑不换图直接保存 → 不产生新文件，无孤儿。
3. 编辑换封面 → 旧封面文件被删，新封面正常。
4. 选图后取消表单 → 无持久文件产生。
5. 让 `storeImage` reject → 提示失败，菜谱未入库，按钮恢复可点。

**重置/订单**：
1. 新增若干带图菜谱 → `readdirSync(IMG_DIR)` 有文件 → 点「恢复系统演示数据」→ 目录为空，厨房页回到 3 个默认菜谱。
2. 标记订单完成/删除订单 → 状态持久（重启仍在）；order 页全文搜 `wx.setStorageSync` 为 0。

**全链路**：新增 → 重启 → 编辑换图 → 删除 → 重置，全程图片与数据正确。
